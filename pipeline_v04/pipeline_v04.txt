# MeasureTrace 파이프라인 v4 — 기술 명세

짝 문서: `MeasureTrace_오류코드_E01-E07_기술명세.md`

이 문서는 현재 설계한 처리 흐름과 검사 기준을 설명합니다.

---

## 1. 무엇을 만드는가

**MeasureTrace** — 연구 계획서의 계산식으로 원시 데이터를 다시 계산해, **최종 보고서 초안의 수치 주장이 그 데이터로 지지되는지** 판정하는 감사 에이전트.

### 1-1. 판정
| 판정 | 뜻 |
|---|---|
| **Supported** | 재계산값이 주장과 일치하고, 판정을 바꾸는 오류 코드가 없음 |
| **Unsupported** | 재계산값과 불일치하거나, 재계산할 근거(식·데이터·단위·승인)가 없음. 이유는 오류 코드로 표시 |
| 검사 대상 아님 | 판정이 아니라 분류. 문헌 인용 문장, 수치와 연결되지 않는 정성 문장 |

- 재계산 근거가 없으면 Unsupported로 판정하고 원인을 E06 등으로 구분합니다.
- 판정에 영향을 주지 않는 사실은 오류 코드의 **기록**으로 남깁니다(E02 진행 결정, E07).

### 1-2. 판정하지 않는 것
- 계산식 자체의 과학적 타당성 — **연구 계획서의 식과 설계를 신뢰**합니다
- 첫 실행 이전에 삭제·수정된 데이터
- 그림(Figure) — 그림 판독 과정의 할루시네이션·앵커링 위험 때문에 제외
- 외부 문헌의 수치 — 보고서 안의 인용 표시만 기록, 외부 검색 없음
- 수치와 연결되지 않는 정성 문장
- 과학적 진실, 데이터 조작 여부

---

## 2. 설계 원칙

| # | 원칙 |
|---|---|
| R1 | 수치 계산은 **파이썬이 실행**합니다. 계산 코드는 LLM이 초안을 쓸 수 있으나 **사용자 승인 + 코드 해시 고정 후에만** 실행합니다. LLM 응답 속 숫자를 계산 입력으로 쓰지 않습니다. |
| R2 | 측정값은 LLM 입력에 넣지 않습니다. LLM은 헤더·계획서·사양서·보고서 문장만 봅니다. |
| R3 | 승인되지 않은 식·가공 방법·코드·단위·사양은 계산에 쓰지 않습니다. |
| R4 | 블라인드 검증을 위해 **보고서는 RECOMPUTE가 끝난 뒤 VALIDATE에서 처음 엽니다.** |
| R5 | 입력은 읽기 전용이며 산출물은 입력 밖 폴더에 씁니다. 원본은 지우지 않습니다. |
| R6 | 입력 폴더의 스크립트는 실행하지 않습니다. 승인된 코드만 격리된 환경에서 실행합니다. |
| R7 | 모든 판정에 근거(데이터 해시·코드 해시·계산 로그·보고서 쪽·문장 번호)를 남기고 LLM 호출은 감사 로그에 기록합니다. |

---

## 3. 입력

| 입력 | 형식 | 비고 |
|---|---|---|
| RAW_DATA | CSV 등 | 계산의 유일한 데이터 입력 |
| 연구 계획서 | **.docx** | 계산식은 **Word 수식(OMML)**, 가공 방법·설계(독립 단위·반복 수)·검정 방법 포함 |
| 장비 사양서 | PDF | 측정 범위·오차 |
| 최종 보고서 초안 | 문서 | **별도 경로**로 입력, 5-1 전까지 열지 않음 |

사용하지 않음
- **PROCESSED_DATA** — 연구자가 이미 계산한 값이라, 이것으로 재계산하면 연구자의 숫자로 연구자의 숫자를 검증하는 순환이 됨. raw를 가공해야 하는 값은 Agent AI가 계획서의 가공 방법으로 직접 계산
- **Figure**, 외부 문헌

## 4. 파이프라인 — 6단계 · 17개 과업

```
1 INGEST     1-1 입력 격리·분류   1-2 해시 2종        1-3 산출물 이력 장부
2 EXTRACT    2-1 입력 데이터 분석 2-2 측정 조건 추출  2-3 데이터 구조화   2-4 누락 점검
3 CONFIRM    3-1 데이터 해석 승인 3-2 장비 사양 확인  3-3 데이터 이상 확인        ↺ 최대 3회
4 RECOMPUTE  4-1 수치 재계산      4-2 계산 로그
5 VALIDATE   5-1 주장 추출·분류   5-2 재계산값과 비교 5-3 오류 코드 분류
6 AUDIT      6-1 결과 출력        6-2 수정 후 재평가                              ↻ 1부터
```

주체 표기: `[PY]` 파이썬 · `[LLM]` 해석·코드 초안 · `[USER]` 연구자 승인

### 1 INGEST — 격리하고 지문을 고정한다 `[PY]`

| 과업 | 내용 |
|---|---|
| **1-1 입력 격리·분류** | 입력 폴더는 읽기만 하고 산출물은 입력 밖 폴더에 쓴다. 보고서는 별도 경로로 받는다(물리적으로 다른 폴더 가능). 파일을 RAW / 연구 계획서 / 장비 사양서 / 보고서로 분류 |
| **1-2 해시 2종** | 파일마다 원본 바이트 해시 + 내용 정규화 해시(CSV: BOM·개행·후행 공백 제거 후). 바이트만 다르고 내용이 같으면 "형식만 변경". **행·열 차이**를 보려면 이전 실행의 내용(또는 행별 해시)을 저장해 비교해야 함 — 해시만으로는 "달라졌다"까지만 알 수 있음 |
| **1-3 산출물 이력 장부 (lineage)** | 파이프라인이 입력을 가공해 **만들어 낸** 중간 산출물마다 `(입력 해시, 코드 해시, 파라미터) → 출력 해시`를 한 줄씩 기록 |

- 측정 시각은 현재 검사 규칙의 입력으로 사용하지 않습니다.

### 2 EXTRACT — 식·조건·데이터를 파악한다 (LLM은 측정값을 보지 않음)

**2-1 입력 데이터 분석**
- **a `[LLM]` 데이터 내용 파악** — 행·열 **헤더만** 읽고 무엇을 측정한 데이터인지 판단. 측정값은 읽지 않음
- **b `[PY]` 계획서 수식 변환** — docx 안의 Word 수식(`m:oMath`)을 dwml로 LaTeX로 변환. 수식마다 앞 문단 문장·수식 해시를 함께 저장(`equations.json`). 구현 메모는 9장
- **c `[LLM]` 연구 내용 추출** — 식, **가공 방법**(raw → 계산 입력값), **설계**(독립 단위·반복 수), 검정 방법을 추출하고 **실험 ↔ 데이터 ↔ 식 ↔ 장비** 매칭표와 **계산 코드 초안**을 작성

**2-2 측정 조건 추출** `[LLM]`
- 장비 사양서에서 측정 범위·오차·유효 범위를 추출(쪽 번호·원문 인용 포함)

**2-3 데이터 구조화** `[PY]`
- **파이썬만** 값을 직접 읽어 단위 누락·모호한 단위·결측·이상치(2-2의 사양 범위 이탈)를 확인
- 이상치 판정은 **잠정** 표시 — 사양이 아직 승인 전이므로
- → 오류 코드 E01, E02

**2-4 누락 점검** `[LLM]→[PY]`
- LLM이 계획서에서 결론에 필요한 파일·시료·측정 목록을 추출 → 파이썬이 실제 파일과 대조
- → 오류 코드 E03

### 3 CONFIRM — 사람이 확정한다 `[USER]`

모든 답변은 **답변 내용·응답자·시각**과 함께 기록하고, 재실행 시 **해시 차이**를 기록. 보고서 수치는 어떤 질문에도 나오지 않는다(보고서를 아직 열지 않았으므로).

**3-1 데이터 해석 승인** (2-1, 2-4 결과)
- LaTeX 식 · **가공 방법** · 설계 · 매칭표 · 계산 코드를 나란히 보여주고 승인
- 승인된 코드는 **해시를 떠서 고정**하고, 같은 입력이면 재사용 → LLM이 매번 다른 코드를 쓰는 문제 방지
- 누락 목록(E03) 확인
- 예시 질문: "수식 A를 사용해 이렇게 계산한 게 맞나요?" / "장비 Z로 측정값 K를 확인한 게 맞나요?" / 실험 ↔ 데이터 ↔ 식 ↔ 장비 관계를 도식으로 제시
- 틀린 해석은 고칠 내용을 입력받아 EXTRACT 재실행

**3-2 장비 사양 확인** (2-2 결과)
- 예: "장비 사양서를 읽어 보니 측정 조건 α에서 오차 n %라고 나오는데, 맞게 읽었나요?"
- **고쳐지지 않으면** 2-3의 잠정 이상치를 확정, **고쳐지면** 2-3을 다시 계산

**3-3 데이터 이상 확인** (2-3 결과)
- 단위 누락·모호: 단위를 제안하고 사용자 입력을 받음
- 결측·이상치: 해당 파일·행·열을 보여주고 선택
  - 재측정 → 파일 재업로드 → INGEST로 돌아감 (원본은 지우지 않음)
  - 충분히 나올 수 있는 값으로 인지 → 그대로 진행 (결정을 기록)

**피드백 루프 규칙**
- 피드백 과정 **최대 3회**. 바뀐 항목만 다시 묻는다
- 3회 뒤에도 미확정인 항목에 의존하는 주장은 **Unsupported**(E06 사유 "미확정")
- 여러 번 도는 예: ① 식을 고쳤더니 다른 식의 열 매칭이 바뀜 ② 단위를 mA로 확정했더니 사양 범위와 비교해 새 이상치가 드러남 ③ 재업로드한 파일에 새 열이 생김

### 4 RECOMPUTE — 승인된 코드로 재계산한다 `[PY]`

**4-1 수치 재계산**
- 입력은 **RAW만**. 승인된 가공 방법·식·코드로 raw → 중간값 → 최종값을 계산
- 보고서는 아직 열지 않음(블라인드)

**4-2 계산 로그**
- 사용한 데이터의 해시 2종 · 계산 과정 · 결과값 · 결과 해시 · **코드 해시**
- 다음 실행에서 데이터 해시를 비교해 데이터가 바뀌었는지 판단(E07)

### 5 VALIDATE — 보고서를 처음 열고 대조한다

**5-1 주장 추출·분류** `[LLM]`
- 보고서 문장을 추출하고 **쪽 번호·문장 번호**를 기록
- 문장 분류

| 분류 | 처리 |
|---|---|
| 자기 데이터 수치 주장 | 검사 |
| 방향 주장("A가 B보다 높다", "증가했다") | 검사 — 재계산값의 차이 부호 |
| 유의성 주장("유의하게") | 계획서에 검정 방법이 있으면 검사, 없으면 방향만 검사 + E06 사유 "검정 방법 없음" |
| 정도 표현("크게 증가") | 방향만 검사, "크게"는 판정 제외 표시 |
| 문헌 인용([3], et al., "보고된 바") | 검사 대상 아님 — 인용 번호·참고문헌 원문만 기록 |
| 혼합("우리 값 3.1 eV는 문헌값 3.2 eV와 유사") | 우리 값만 검사, 문헌값은 기록 |
| 수치와 연결되지 않는 정성 문장 | 검사 대상 아님 |

**5-2 재계산값과 비교** `[PY]`
- 수치: 재계산값을 **보고서 수치의 유효 자릿수로 반올림**해 일치 여부 판단(6장)
- 방향: 차이 부호 / 유의성: 계획서 검정으로 재계산한 결과
- 단위 환산, 보고된 n·자유도와 계획서 설계 대조
- 주장에 대응하는 재계산값이 없으면 E06

**5-3 오류 코드 분류** `[PY]`
- 주장마다 판정 + 오류 코드 + 사유 부여 (`MeasureTrace_오류코드_E01-E07_기술명세.md`)

### 6 AUDIT — 결과를 내고, 고치면 다시 본다

**6-1 결과 출력**
- Supported / Unsupported(+오류 코드) / 검사 대상 아님 목록
- 주장마다 보고서 원문(쪽·문장) · 보고값 · 재계산값 · 사용한 식 · 데이터 해시를 나란히 표시
- 설명 문장은 LLM이 쓸 수 있으나 숫자는 파이썬이 채움

**6-2 수정 후 재평가**
- 연구자가 고치고 다시 실행 → 1부터 재실행, 수정 전·후 판정 비교
- 이전 실행의 데이터 해시와 비교(E07)

## 5. 실행 순서와 되돌아가는 경로

```
1-1 → 1-2 → 1-3
 → 2-1(a→b→c) → 2-2 → 2-3(잠정) → 2-4
 → 3-1 · 3-2 · 3-3  ─┬─ 수정 → EXTRACT 재실행 (최대 3회)
                     └─ 재업로드 → INGEST
 → 4-1 → 4-2
 → 5-1(보고서 첫 열람) → 5-2 → 5-3
 → 6-1 → (연구자 수정) → 6-2 → 1-1
```

블라인드 입증: 계산 로그의 시각 < 보고서 열람 시각을 기록으로 남긴다.

## 6. 허용오차 — 두 종류[결정]

| 구분 | 무엇과 무엇 | 기준 |
|---|---|---|
| ① 도구 정확도 | MeasureTrace 재계산값 vs 벤치마크 정답(반올림 전) | **상대 오차 ≤ 1e-6** (대회 제출 계획서 기준) |
| ② 주장 판정 (E05) | MeasureTrace 재계산값 vs 보고서 수치 | 재계산값을 **보고서 수치의 유효 자릿수로 반올림**해 같으면 일치 |

- ①을 주장 판정에 그대로 쓰면 반올림된 보고값(예: "7.6 nS" vs 7.62)이 전부 Unsupported가 되므로 둘을 분리
- 절대 오차는 단위에 따라 의미가 달라지므로 쓰지 않음(예: 5×10⁻⁸ S는 0과의 차이도 1e-6 이하)

## 7. 구현 및 데모 검증 항목

| # | 확인 항목 | 이유 |
|---|---|---|
| 1 | 실제 Word 수식 편집기로 입력·저장한 `.docx`로 수식 변환 시험 | 손으로 만든 XML만으로는 Word 출력 구조를 검증할 수 없음 |
| 2 | 데모 연구 계획서에 Word 수식, 설계, 가공 방법, 검정 방법 포함 | 계산 경로를 승인·재현하기 위한 입력 |
| 3 | 데모 데이터와 주입할 오류 확정, 오류를 심는 사람과 검사 규칙 작성자를 분리 | 검출 성능 과대평가 방지 |
| 4 | 생성형 AI 사용 내역을 기록하고 제출 규정에 맞게 공개 | 제출물의 출처 확인 |
| 5 | 팀원 PC에서 필요한 패키지 import와 전체 실행 흐름 확인 | 환경 차이 점검 |

## 8. Word 수식 변환 요구사항

- `.docx`를 ZIP으로 열어 `word/document.xml`의 본문 문단(`w:p`)에서 수식 요소(`m:oMath`)를 찾습니다.
- 각 수식을 `dwml.omml.oMath2Latex(element)`로 변환하고, 수식 위치·OMML 해시·계획서 해시를 함께 기록합니다.
- 문단에 포함된 수식은 직접 찾아 변환합니다. 변환 실패는 수식 단위로 기록하고, 사용자 확인 대상에 넣습니다.
- 수식 속성 요소가 빠진 경우 변환 예외가 발생할 수 있으므로 전체 문서 처리를 중단하지 않습니다.
- 유니코드 기호의 LaTeX 출력은 실제 Word 문서로 확인합니다. 출력 문자열을 임의로 보정하지 않습니다.
