# MeasureTrace 파이프라인 — Git_v6 구현 기준

기준 코드: `Git_v6/measuretrace` · `Git_v6/web`

이 문서는 Git_v6 코드가 **실제로 하는 처리 흐름**을 정리합니다.

---

## 1. 무엇을 만드는가

**MeasureTrace** — 연구 계획서의 계산식으로 원시 데이터를 다시 계산해, **최종 보고서 초안의 수치 주장이 그 데이터로 지지되는지** 판정하는 감사 에이전트.

### 1-1. 판정
| 판정 | 뜻 |
|---|---|
| **Supported** | 재계산값이 주장과 일치하고, 판정을 바꾸는 오류 코드가 없음 |
| **Unsupported** | 재계산값과 불일치하거나, 재계산할 근거(식·데이터·단위·승인)가 없음. 이유는 오류 코드로 표시 |
| 검사 대상 아님 | 판정이 아니라 분류. 문헌 인용 문장, 수치와 연결되지 않는 정성 문장 |
| 구조화 실패 | 5-1에서 LLM 응답이 파이썬 검사를 끝내 통과하지 못한 문장(결과에 따로 표시) |

판정은 "제출된 자료가 이 주장을 지지하는가"에 대한 것입니다. 계산식의 과학적 타당성, 그림, 외부 문헌 수치, 데이터 조작 여부는 판정하지 않습니다.

---

## 2. 설계 원칙

한 줄 요약: **"Agents propose, Python verifies, humans approve."**

| # | 원칙 | Git_v6에서 지키는 방법 |
|---|---|---|
| R1 | 수치 계산은 파이썬이 실행. LLM 응답 속 숫자를 계산 입력으로 쓰지 않음 | 계산 코드는 LLM이 초안만 쓰고, 3 CONFIRM 승인 + 해시 고정 뒤 4단계에서만 실행 |
| R2 | 측정값은 LLM에 보내지 않음 | 2-1a는 헤더 요약 JSON의 정해진 키만, 5-1은 숫자를 `⟨Nk⟩`로 가린 문장만 — 에이전트 계약의 입력 검사(`guard_input`)가 어기면 보내지 않음 |
| R3 | 승인되지 않은 식·가공·코드·단위·사양은 계산에 쓰지 않음 | `confirmed.json`(인계 계약)에 들어간 것만 뒷단이 읽음 |
| R4 | 보고서는 RECOMPUTE가 끝난 뒤 VALIDATE에서 처음 연다 | 1단계는 보고서 원본 해시만, 5-1이 `blind_log.json`에 "계산 로그 완료 시각 < 보고서 열람 시각"을 남기고 아니면 멈춤 |
| R5 | 입력은 읽기 전용, 산출물은 입력 밖 | `workspace/inputs/<실행>`은 읽기 전용 사본, 산출물은 `workspace/outputs/…` |
| R6 | 입력 폴더의 스크립트는 실행하지 않음. 승인 코드만 격리 실행 | 스크립트는 "실행 안 함"으로 분류만. 승인 코드는 별도 프로세스(`python -I`)에서 1회 |
| R7 | 모든 판정에 근거를 남기고 LLM 호출은 감사 로그에 기록 | 데이터·코드·결과 해시, 쪽·문장 번호, `llm_audit.jsonl`, 1-3 이력 장부 |

## 3. 입력

| 입력 | 형식 | 비고 |
|---|---|---|
| RAW 데이터 | CSV·TSV·TXT·DAT·XLSX | 계산의 유일한 데이터 입력 |
| 연구 계획서 | **.docx** | 계산식은 Word 수식(OMML). 가공 방법·설계·검정 방법 포함 |
| 장비 사양서 | PDF | 측정 범위·오차 |
| 최종 보고서 초안 | docx·pdf·md·txt | **별도 경로(report 구역)**로 입력, 5-1 전까지 열지 않음 |

1-1 분류 결과(규칙만, LLM 없음 — 확정은 3 CONFIRM)

| 분류 | 처리 |
|---|---|
| `raw` RAW 데이터 · `plan` 연구 계획서 · `spec` 장비 사양서 · `report` 보고서 | 다음 단계로 넘어감 |
| `processed` 가공 데이터 | **사용 안 함** — 연구자의 숫자로 연구자의 숫자를 검증하는 순환 방지. 파일명(summary·평균·결과…)이나 열 이름(mean·std…)으로 판별 |
| `figure` 그림 | 사용 안 함 |
| `script` 스크립트(.py·.ipynb·.r …) | 실행 안 함 |
| `system` 시스템·임시 파일 | 제외 |
| `unknown` 미분류 | 확인 필요 |

## 4. 코드 구성

```
Git_v6/
  measuretrace/
    ingest/      1 INGEST        workspace(사본·잠금) · classify · hashing · run
    extract/     2 EXTRACT       equations(2-1b) · headers(2-1a) · spec(2-2) · plan(2-1c) · smoke(2-1c 합성 데이터 실행 검사) · datacheck(2-3) · missing(2-4) · tables · units
    confirm/     3 CONFIRM       items(질문 만들기) · run(start/submit, 최대 3회) · dashboard(한 화면 일괄 승인)
    recompute/   4 RECOMPUTE     run(화면용 기록) · sandbox(코드 규칙·정적 점검)
    bridge.py    앞단 → 뒷단 연결 (인계 묶음 만들기 · 승인 봉인 · 뒷단 호출)
    backend/     4·5·6 뒷단      contract(인계 계약) · recompute/engine·_runner · validate/* · audit/* · pipeline
    agents.py    에이전트 계약 (입력 검사 · 스키마 · 파이썬 검사기 · 재시도)
    llm.py · backend/common/llm.py   LLM 호출(캐시 · 감사 기록) · gemini_adapter.py
    formula/     수식 코드 기호 검증(SymPy) — ※ 현재 파이프라인에 연결되어 있지 않음 (8장)
  web/           로컬 웹 화면 (server.py + static/*.js)
  tests/         자동 시험 (pytest, LLM 없음)
  workspace/     inputs/ · outputs/ · llm_cache/
```

앞단(1~3)과 뒷단(4~6)은 **`backend/contract.py`의 `confirmed.json` 형식으로만** 주고받습니다. 이 형식을 바꾸면 팀 전체에 공지해야 합니다.

## 5. 파이프라인 — 6단계

```
1 INGEST     1-1 입력 격리·분류   1-2 해시 2종          1-3 산출물 이력 장부
2 EXTRACT    2-1a 헤더 해석       2-1b 수식 변환        2-1c 연구 내용·코드 초안   2-2 측정 조건   2-3 데이터 구조화   2-4 누락 점검
3 CONFIRM    3-1 데이터 해석 승인 3-2 장비 사양 확인    3-3 데이터 이상 확인                 ↺ 최대 3회
4 RECOMPUTE  4-1 수치 재계산      4-2 계산 로그
5 VALIDATE   5-1 주장 추출·분류   5-2 재계산값과 비교   5-3 오류 코드 분류
6 AUDIT      6-1 결과 출력        6-2 수정 후 재평가                                          ↻ 1부터
```

주체 표기: `[PY]` 파이썬 · `[LLM]` 해석·코드 초안 · `[USER]` 연구자 승인

### 1 INGEST — 격리하고 지문을 고정한다 `[PY]`

| 과업 | 내용 |
|---|---|
| **1-1 입력 격리·분류** | 웹에서 올린 파일을 실행마다 새 폴더에 **사본**으로 받고 **읽기 전용으로 잠금**. 연구 자료(`data`)와 보고서(`report`)는 다른 폴더. 3장의 규칙으로 분류 |
| **1-2 해시 2종** | 파일마다 원본 바이트 해시 + 내용 정규화 해시. 표는 **행별 해시**도 남겨 다음 실행과 행·열 차이를 봄. 같은 프로젝트의 이전 실행과 비교해 "형식만 변경" / "내용 변경 + 행·열 차이"를 기록 |
| **1-3 산출물 이력 장부** | `(입력 해시, 코드 해시, 파라미터) → 출력 해시`를 `lineage.jsonl`에 한 줄씩 추가만 함. 연구자가 가져온 파일은 적지 않음 |

내용 정규화 방법(방법 이름을 함께 기록 — 방법이 다르면 내용 해시끼리 비교하지 않음)

| 방법 | 대상 | 정규화 |
|---|---|---|
| `text-v2` | CSV·TSV·TXT·DAT·MD | BOM 제거 → 개행 `\n` 통일 → 줄 끝 공백 제거 → 빈 줄 제거 |
| `docx-text-omml-v1` | 연구 계획서 | 문단 글자 + Word 수식 XML(정규형). zip 재압축·메타데이터 차이 무시 |
| `pdf-text-v1` | 장비 사양서 | 모든 쪽의 글자(쪽 경계 포함). 글자층이 없으면 원본 해시만 |
| `xlsx-cells-v1` | 엑셀 | 시트별 칸 값·수식 |
| `none` | 그 밖 · 보고서 | 원본 해시 그대로 (보고서는 5-1 전까지 열지 않음) |

- 연구 자료가 하나도 없으면 멈춥니다. 이미 INGEST를 마친 실행은 다시 받지 않습니다(새 실행으로).
- 측정 시각은 모으지 않습니다. LLM을 쓰지 않습니다.
- 산출물: `ingest_snapshot.json`

### 2 EXTRACT — 식·조건·데이터를 파악한다 (LLM은 측정값을 보지 않음)

실행 순서: **2-1b[PY] → (2-1a · 2-2 · 2-4 목록)[LLM] 병렬 → 2-1c[LLM] → 2-3[PY] → 2-4 대조[PY]**
한 과업이 실패해도 나머지는 계속하고 실패를 기록합니다. 보고서는 열지 않습니다.

| 과업 | 주체 | 내용 | 산출물 |
|---|---|---|---|
| **2-1a 데이터 내용 파악** | `[LLM]` HeaderReader | 파일 경로·열 이름·행 수·숫자 열 여부·글자 열(시료·조건·위치)의 고유 표기만 보고 각 열이 무엇을 측정했는지 판단. **숫자 열 값은 한 칸도 보내지 않음.** 같은 열 구성 파일은 한 묶음으로 한 번만 묻고, 보낸 글 전체를 `sent`로 남김 | `headers.json` |
| **2-1b 계획서 수식 변환** | `[PY]` | docx의 `m:oMath`를 **dwml**로 LaTeX 변환. 수식마다 EQ 번호·앞 문장·수식 XML 해시·계획서 해시. 실패는 수식 단위로 잡아 3-1 "직접 적어 달라" 질문 후보로. 계획서 본문(수식 자리는 `[EQnn]`)도 만들어 2-1c·2-4 입력으로 씀 | `equations.json` |
| **2-1c 연구 내용 추출** | `[LLM]` PlanReader | 계획서 본문 + 헤더 해석(값 없음) + 사양 항목 이름으로 식 · **가공 방법** · 설계(독립 단위·반복 수) · 검정 방법 · 실험↔데이터↔식↔장비 매칭표 추출. 인용문은 원문과 글자 그대로 일치해야 하고, 식 번호는 실제 있어야 함 | `plan_extraction.json` |
| **2-1c 계산 코드 초안** | `[LLM]` CodeDrafter | `def compute(files: dict[str, str]) -> dict` 한 함수 → `{"results": [{name, symbol, value, unit, eq_id, condition}], "intermediate": {...}}`. 실제 측정값으로는 **실행하지 않음** — 정적 점검(허용 import 목록, 쓰기 open·eval·exec·subprocess·socket 등 금지) 뒤 **합성 데이터 실행 검사**(아래)를 하고 파일과 해시를 남김 | `code_draft.py` |
| **2-2 측정 조건 추출** | `[LLM]` SpecReader | 사양서에서 측정 범위·오차·유효 범위를 쪽 번호·원문 인용과 함께. 파이썬이 "인용이 그 쪽에 글자 그대로 있나, 최솟값·최댓값 숫자가 인용 안에 있나"를 확인. 확인 안 된 항목도 버리지 않고 표시만 | `spec_conditions.json` |
| **2-3 데이터 구조화** | `[PY]` | 파이썬만 값을 읽어 **단위 누락·모호(E01)**, **결측·사양 범위 이탈(E02)**을 파일·줄·열·값과 함께 기록. 사양이 승인 전이라 범위 이탈은 모두 **잠정**. 도구는 어떤 값도 지우거나 빼지 않음 | `data_checks.json` |
| **2-4 누락 점검** | `[LLM]→[PY]` RequiredDataReader | LLM은 **계획서만** 읽고 필요한 시료·파일·측정 목록을 뽑음(실제 파일 목록은 보여 주지 않음 — 있는 파일에 맞춰 목록을 줄이지 않도록). 파이썬이 실제 파일과 대조 → **E03** 후보 | `missing_check.json` |

**2-1c 합성 데이터 실행 검사** `[PY]` (LLM 없음, 토큰 0) — 정적 점검은 '금지된 것을 쓰지 않았는지'만 보므로, 초안이 **실제로 돌아가는지**를 3-1 승인 전에 확인합니다.
- 입력: 2-1a 헤더 묶음만. 파일 수·열 이름·열 종류를 실제와 같게 만들고, 숫자 칸은 0.5~1.5 난수(seed = 코드 해시 → 결정론, 파일당 최대 60행), 글자 칸은 헤더 요약에 있던 표기를 돌려 씀. **실제 측정값은 쓰지 않음(R2).**
- 실행: 별도 프로세스(`python -I -B`), 시간 제한, 감사 훅으로 네트워크·프로세스 생성·파일 쓰기·허용 밖 읽기 차단.
- 결과: `passed` / `failed` / `error`와 사유(예외 종류·메시지·줄, 결과 형식 문제, 유한하지 않은 결과 이름). 사유에는 합성 값만 있어 LLM에 되돌려도 측정값이 섞이지 않음.
- 실패하면 사유를 `[Feedback from the Python checker]`로 붙여 CodeDrafter에게 **다시 받음**(최대 `MT_SMOKE_REWRITES`회, 기본 2 — 실패할 때만 LLM 호출이 늚). 다시 받은 초안이 정적 점검을 어기면 쓰지 않음. 모든 시도는 `code_rewrites`에 기록.
- 성질 검사: 파일 안 행 순서를 섞어도, 파일 순서를 바꿔도 결과가 같아야 함(상대 1e-9). 기록·표시만 하고 승인을 막지 않음.
- 결과는 `plan_extraction.json`의 `code_smoke_test`로 남고, 3-1 계산 코드 항목에 한 줄 요약으로 표시됨.

- 표 읽기 규칙: 소수점 쉼표(`1,23`)는 구분자가 쉼표가 아니고 그 파일 숫자 칸이 `정수,정수` 꼴만 쓸 때만 소수점으로 봅니다. 그 밖에 쉼표가 든 칸은 숫자로 읽지 않고 2-3 "숫자가 아닌 값"으로 남깁니다.
- 단위 표기: 같은 단위의 다른 표기(`ohm/sq`, `Ω/□` …)는 사전으로 흡수하고, 모르는 표기는 "모호"로 남깁니다.
- 요약: `extract_summary.json`. 산출물마다 1-3 장부에 기록.

### 3 CONFIRM — 사람이 확정한다 `[USER]`

2 EXTRACT 결과에서 **규칙으로** 확인 항목을 만듭니다(LLM 없음). 보고서 수치는 어떤 질문에도 나오지 않습니다(보고서 미개봉).

| 구역 | 항목 종류 | 받을 수 있는 답 |
|---|---|---|
| **3-1 데이터 해석 승인** | 식(equation) · 가공(processing) · 설계(design) · 검정(test) · 매칭(matching) | 승인 / 수정(글) |
| | 계산 코드(code) — 정적 점검 결과와 합성 데이터 실행 검사 요약을 함께 표시 | 승인 / 거절(이유) — 승인하면 **코드 해시 고정** |
| | 누락(missing, E03) | 누락 인정 후 진행 / 추가 업로드(새 실행) / 누락 없음 |
| **3-2 장비 사양 확인** | 사양(spec) · 범위 밖 표시값(overflow) | 승인 / 수정(min·max·unit·글) |
| **3-3 데이터 이상 확인** | 단위(unit, E01) | 단위 표기 입력 |
| | 이상값 묶음(anomaly, E02) | 그대로 진행 / 재측정(새 실행) |
| Q | 2단계 LLM 질문(선택) | 답변 / 건너뜀 |

동작 규칙
- 항목마다 제안(도구가 읽은 것)과 그 해시를 둡니다. **해시가 같으면 앞선 답을 유지하고, 달라지면 다시 묻습니다** — "바뀐 항목만 다시 묻는다".
- **같은 프로젝트의 이전 실행**에서 확정한 항목은 제안 해시가 같으면 이어받습니다. 모든 필수 항목을 이어받으면 바로 확정됩니다.
- 한 번 제출 = 피드백 1회, **최대 3회**. 3-1 수정 → EXTRACT 재실행(LLM), 3-2 수정·3-3 단위 확정 → 2-3을 다시 계산(PY) → 새로 드러난 이상값은 새 항목.
- 3회 뒤에도 남은 필수 항목은 **미확정** → 그 항목에 의존하는 주장은 5단계에서 Unsupported(E06 "미확정").
- **대시보드**: 모든 항목을 한 화면에서 훑고 고친 것만 보내면 나머지는 일괄 승인. 고친 값은 "사용자 입력" 출처로 승인값이 되며(EXTRACT 재실행 없음), 항목마다 `batch_approved` / `edited`(before/after)를 기록.
- 모든 답은 응답자·시각과 함께 `answers.jsonl`에 추가만 합니다. 계산 코드는 여기서도 실행하지 않습니다.
- 산출물: `confirm_state.json` · `answers.jsonl` · `dashboard_approval.json` · **`confirmed.json`**(승인된 식·가공·설계·검정·매칭·사양·단위·결정) · `approved_code.py`. 승인 코드는 `approved_code_registry.jsonl`에 남겨 **같은 입력이면 재사용**합니다.

### 앞단 → 뒷단 연결 (`bridge.py`)

승인 코드는 **뒷단 엔진에서 한 번만** 실행합니다. 보고할 항목 목록(n·df·p 포함)은 계산 전에는 알 수 없으므로 순서가 이렇습니다.

| 순서 | 함수 | 하는 일 |
|---|---|---|
| ① | `run_step4` | 실행 묶음(RAW·식·설계·기록·3-1 승인 코드, 항목 목록 없음)을 만들어 뒷단 `run_discovery`로 **한 번 실행**. 결과 전부와 메타데이터(id·이름·기호·단위·조건·식) 기록 |
| ② | `preview` | 그 결과로 항목 목록을 붙인 전체 묶음을 보여 줌(파일을 쓰지 않음). 화면은 묶음 지문(`bundle_sha256`)을 받아 둠 |
| ③ | `run` | 같은 묶음을 다시 만들어 **지문이 같을 때만** 승인자 이름으로 봉인 → 같은 계산 로그에 항목 결합(재계산 없음) → 5-1 → 5-2 → 5-3 → 6-1 · 6-2 |

변환 규칙(모두 규칙 — LLM 없음)
- 데이터: 1-1의 RAW만. 원본 해시가 1-2 값과 다르면 거부.
- 열: 2-1a 헤더 뜻 · 3-3 확정 단위 > 2-3 헤더 단위. 3회 뒤 미확정 E01 열은 `unit_status=unresolved`.
- 코드: 3-1 승인 본문을 **한 글자도 바꾸지 않고** 싣고, 뒷단 규약 `mt_compute(data, params) → {"outputs", "meta"}`로 옮기는 어댑터를 붙임. 어댑터가 붙은 파일 해시가 인계 코드 해시, 승인 본문 해시는 `params.front_code_sha256`으로 함께 봉인.
- 기록: E02 "그대로 진행" → `proceed`, 재측정·미확정 → `unresolved`, E03 누락 → `missing`, 3회 뒤 미확정 → `pending`.

### 4 RECOMPUTE — 승인된 코드로 재계산한다 `[PY]`

**4-1 수치 재계산**
- 입력은 **RAW만**. 승인된 가공 방법·식·코드로 raw → 중간값 → 최종값.
- 실행 전 확인(하나라도 어긋나면 실행하지 않고 이유를 남김): 승인 코드 해시 · 추출 결과가 확정 때와 같음 · RAW 해시 · 정적 점검 · 미확정 없음.
- 실행 방식: 별도 프로세스(`python -I`, 최소 환경 변수, 시간 제한, 출력 폴더 안의 작업 폴더). RAW는 해시를 확인한 실행별 사본만 넘기고, runner가 파일·네트워크 접근을 제한합니다. **운영체제 수준 샌드박스(컨테이너·VM)는 아닙니다.**
- 보고서는 아직 열지 않습니다. 계산 시각을 남겨 5-1 열람 시각보다 앞섬을 입증합니다.

**4-2 계산 로그**
- 사용한 데이터의 해시 2종 · 계산 과정 · 결과값 · 결과 해시 · 코드 해시.
- 뒷단 `runs/<뒷단 실행>/calc_log.json`(탐색 실행은 `calc_log_discover.json`)이 근거이고, 앞단 `recompute/calc_log.json`은 화면용 요약입니다.
- E07 미리보기: 같은 프로젝트의 이전 4단계 기록과 데이터 해시를 비교해 행·열 차이를 보여 줍니다(판정에 붙는 E07은 6-2가 남김).

### 5 VALIDATE — 보고서를 처음 열고 대조한다

**5-1 주장 추출·분류** `[LLM]` ClaimExtractor
- 블라인드 확인: 4-2 계산 로그가 끝난 뒤에만 보고서를 열고, 열람 시각을 `blind_log.json`에 남깁니다.
- 보고서 읽기: 문장마다 **쪽 번호·문장 번호**(`p3.s12`). docx는 쪽 정보가 없어 `w:lastRenderedPageBreak` → 명시적 쪽 나눔 순으로 세고, 둘 다 없으면 전부 1쪽(근사값임을 기록). PDF는 pdfplumber 쪽 번호.
- 마스킹: 문장 안 숫자마다 ID(`p3.s12.n2`)를 붙이고 LLM에는 `⟨N2⟩`처럼 **가려서** 보냅니다. LLM은 ID를 가리키기만 하고 파이썬이 원래 글자로 되돌립니다(숫자는 문자열 — `7.6`과 `7.60`의 유효 자릿수 보존). 인용 표시(`[3]`)의 숫자는 숫자로 보지 않습니다. **식별자 번호**(`sample 12`, `Fig. 3`, `Table 2`, `Eq. 1`, `시료 7` — 쉼표·and로 이어진 목록 포함)와 **연도**(19xx·20xx, 바로 뒤가 단위가 아닐 때)는 가리지 않고 보여 줍니다. 어느 시료의 주장인지 알 수 있어야 하고, 번호가 붙지 않으니 LLM이 값으로 고를 수도 없습니다.
- 숫자나 비교·유의성 표현이 있는 문장만 보내고 나머지는 "보내지 않음"으로 기록합니다.
- LLM이 보는 것: 가린 문장, 승인된 재계산 항목의 이름·설명·단위·집단(**값 없음**), 검정 이름.
- 파이썬 검증: 문장·숫자 ID가 실제 있나, 인용이 글자 그대로인가, 단위·통계량이 원문에 있나, 항목 id가 실제 있나.

| 분류 | 처리 |
|---|---|
| 자기 데이터 수치 주장 | 검사 |
| 방향 주장("A가 B보다 높다") | 검사 — 재계산값 차이의 부호 |
| 유의성 주장("유의하게") | 계획서 검정이 있으면 검사, 없으면 E06 "검정 방법 없음" |
| 정도 표현("크게 증가") | 방향만 검사, "크게"는 판정 제외 표시 |
| 문헌 인용 · 수치와 연결 안 되는 정성 문장 | 검사 대상 아님 (인용·참고문헌은 기록) |

**5-2 재계산값과 비교** `[PY]`
- 수치: 재계산값을 보고 단위로 환산(pint) → **보고 수치의 유효 자릿수로 반올림**해 비교 → 다르면 E05. 환산이 안 되거나 10^k배 차이면 E01.
- 방향: 차이 부호(E05). 유의성: 계획서 검정의 재계산 p값 < 유의수준(E05).
- n·자유도: 계획서 설계에서 나오는 값과 대조(E04).
- 대응하는 재계산값이 없으면 E06(사유: 식 없음 / 데이터 없음 / 미확정 / 검정 방법 없음).
- **불일치 원인 가설**(판정은 바꾸지 않음): 수치·자유도 불일치마다 고정된 8가지를 항상 같은 순서로 시험합니다.

| # | 가설 | 비고 |
|---|---|---|
| 1 | 단위가 10^k배로 적힘 | |
| 2 | 반올림 대신 버림 | |
| 3 | 모표준편차 ↔ 표본표준편차 (n ↔ n−1) | |
| 4 | 표준편차 ↔ 표준오차 (×√n) | |
| 5 | 다른 n으로 나눔 (n−1 또는 n+1) | |
| 6 | 평균 ↔ 중앙값 | 시료별 값 필요 |
| 7 | E02로 표시된 시료 제외 (1개씩, 그다음 전부) | 시료별 값 필요. E02 표시 대상만 후보 — 아무 시료나 빼 보지 않음 |
| 8 | 보고서의 n으로 자유도 계산 (n을 전체 / 집단당으로 읽기) | 보고 자유도가 설계와 다를 때(E04) |

  - 시료별 값: 승인 코드가 계산 과정(`steps`)에 `{"output": <항목 id>, "per_unit": {시료 id: 값}}`을 남기면 씁니다. 없으면 6·7번은 `not_tested (needs per-unit values in steps)`로 기록합니다.
  - 주장당 시도 후보는 최대 30개. 시도한 가설 수를 함께 남기고, 2개 이상 맞으면 `ambiguous`. 리포트에는 "Possible cause (not a verdict)"로만 적습니다.

**5-3 오류 코드 분류** `[PY]`
- 5-2 비교 코드에 더해, 주장이 쓰는 재계산 항목의 **의존 관계**를 따라 앞단 기록(E01 미확정 · E02 · E03 · 미확정 E06)과 E07을 붙입니다.
- 판정을 바꾸는 코드(`effect=unsupported`)가 하나라도 있으면 Unsupported, 아니면 Supported.

### 6 AUDIT — 결과를 내고, 고치면 다시 본다

**6-1 결과 출력**
- `audit_result.json` + `audit_report.md`(영문, "Why" 줄 밑에만 한국어 번역) + `evidence_graph.html`.
- 주장마다 보고서 원문(쪽·문장) · 보고값 · 재계산값(보고 자릿수로 반올림한 값 포함) · 사용한 식 · 코드 해시 · 데이터 해시.
- 판정·숫자·사유 문장은 **파이썬 고정 템플릿**. LLM(NoteSelector)은 정해진 안내 문구 중 하나만 고르고, 재시도는 없습니다(`max_retries=0`). 문장에 숫자가 있거나 정의되지 않은 자리표시자를 쓰면 거절하고 템플릿을 씁니다.
- 증거 사슬 그래프: `Data(sha256) → Formula → Code(sha256) → Recomputed → 보고 자릿수 반올림 → Compare ← Reported(문장) → Verdict`. 원인 가설이 맞으면 "Possible cause" 가지를 붙이고, 시험했는데 맞는 가설이 없으면 "No tested alternative reproduces the value"를 적습니다. 외부 라이브러리·네트워크 없는 정적 HTML 한 장입니다.
  - 맨 위 **블라인드 입증** 줄: 실행 ID · 데이터 해시 요약 · 승인 코드 해시 · RECOMPUTE 완료 시각 · 보고서 첫 열람 시각 → `✓ Blind order verified` / `✗ Warning` / `? not verifiable`.
  - **필터**: 판정(Supported / Unsupported / Not checked / unclassified)과 오류 코드로 거르기. 판정은 색만이 아니라 글자·기호(✓ ✗ – ?)로도 구분.

**6-2 수정 후 재평가**
- 이전 실행 계산 로그의 해시 2종과 비교 → **E07(기록)**: 바이트만 다르면 "형식만 변경", 내용이 다르면 행별 해시로 추가·삭제 행 수("sample_07 파일 3행 감소").
- 판정 변화: 항목·검정 중심 의미 키로 짝지어 수정 전·후 판정을 비교합니다(보고값이 바뀐 주장도 연결). 이전 실행은 자동 선택합니다.
- 첫 실행 이전에 삭제된 데이터는 알 수 없습니다(판정 범위 밖).

## 6. 실행 순서와 되돌아가는 경로

```
1-1 → 1-2 → 1-3
 → 2-1b → (2-1a · 2-2 · 2-4 목록) → 2-1c(식·코드 초안) → 2-3(잠정) → 2-4 대조
 → 3-1 · 3-2 · 3-3  ─┬─ 3-1 수정 → EXTRACT 재실행 (최대 3회)
                     ├─ 3-2 수정 · 3-3 단위 → 2-3 재계산
                     └─ 재측정 · 추가 업로드 → 새 실행(INGEST)
 → [bridge] run_step4 → 4-1 → 4-2 (탐색 실행 1회)
 → [bridge] preview → 사람이 묶음 확인 → run(봉인)
 → 5-1(보고서 첫 열람) → 5-2 → 6-2 데이터 비교(E07) → 5-3 → 6-1 → 6-2 판정 비교
 → (연구자 수정) → 1-1
```

- 6-2의 데이터 비교는 5-3이 E07을 붙일 수 있도록 5-3 **앞에서**, 판정 비교는 6-1 결과를 만든 **뒤에** 합니다.
- 이미 감사한 실행을 다시 감사하면 4단계를 새로 실행합니다(한 뒷단 실행 = 계산 한 번 + 감사 한 번).

## 7. 에이전트 계약 (`agents.py`)

에이전트는 이름이 아니라 **계약**입니다. LLM을 부르는 모든 곳이 호출 종류(kind)로 계약을 찾아 코드로 강제합니다.
① 허용 입력 검사(어기면 보내지 않음) → ② 출력 스키마 → ③ 에이전트별 파이썬 검사기 → ④ ②·③ 실패 시 문제 목록을 `[Feedback from the Python checker]`로 붙여 **최대 2회 재시도**(모든 시도 감사 기록) → ⑤ 같은 (모델, 지시문, 입력, 스키마, effort)면 캐시.
에이전트끼리는 대화하지 않고, 정해진 JSON 산출물로만 주고받으며 순서는 결정론적 상태 기계가 정합니다.

| 에이전트 | 단계 | 역할 | 받는 것 | 절대 보내지 않는 것 | 파이썬 검사 |
|---|---|---|---|---|---|
| HeaderReader | 2-1a | 헤더로 열의 뜻 추정 | 헤더 요약 JSON(경로·열 이름·행 수·글자 표기) | 숫자 칸 값 | 스키마 |
| PlanReader | 2-1c | 식·가공·설계·검정 구조화 | 계획서 본문(`[EQnn]` LaTeX)·헤더·사양 항목 이름 | 측정값·보고서 | 스키마 · 식 번호 실재 · 인용 원문 일치 |
| CodeDrafter | 2-1c | 계산 코드 초안(승인 전 실제 데이터로 실행 안 함) | 계획서·헤더·PlanReader 출력 · 합성 데이터 검사 실패 사유 | 측정값·보고서 | 스키마 · 정적 점검 · `compute()` 정의 · 합성 데이터 실행 검사(실패 시 최대 2회 다시 받기) |
| SpecReader | 2-2 | 사양 범위·오차를 쪽 인용과 함께 | 사양서 글 | 측정값·계획서·보고서 | 스키마 · 쪽 안 인용 확인 |

## 9. 허용오차 — 두 종류

| 구분 | 무엇과 무엇 | 기준 |
|---|---|---|
| ① 도구 정확도 | 재계산값 vs 벤치마크 정답(반올림 전) | 상대 오차 ≤ 1e-6 |
| ② 주장 판정(E05) | 재계산값 vs 보고서 수치 | 재계산값을 **보고 수치의 유효 자릿수로 반올림**해 같으면 일치 |

②의 자릿수 규칙: 소수점이 있으면 그 자릿수까지(`7.60` → 0.01 단위) · 소수점 없는 정수는 끝의 0을 유효숫자로 보지 않음(`1200` → 100 단위) · 과학 표기(`3.2e-5`, `3.2×10⁻⁵`) 지원 · 사사오입(ROUND_HALF_UP).

## 11. 실행 방법

```
python web/server.py                        # http://127.0.0.1:8765 (브라우저 자동 열림)
python web/server.py --port 9000 --no-browser
```

- 화면 흐름: 파일·폴더 끌어 놓기 → [시작] → 1 INGEST → 2 EXTRACT(LLM) → 3 CONFIRM(대시보드) → 4 RECOMPUTE → 인계 묶음 확인 → 5·6 감사(LLM).
- 시험: `python -m pytest -q tests` (LLM 없음, 토큰 0)
- 서버는 이 컴퓨터(127.0.0.1)에서만 열리고, Host·Origin을 확인하며, 쓰기 요청에는 `X-MeasureTrace` 헤더를 요구합니다.

LLM 설정(`.env` 또는 환경 변수 — 키 값은 어디에도 출력하지 않음)

| 변수 | 뜻 |
|---|---|
| `LLM_PROVIDER` | `gemini` 또는 `anthropic`(기본 anthropic). **Git_v6의 `.env`는 `gemini`** |
| `GEMINI_API_KEY`(또는 `GOOGLE_API_KEY`) · `GEMINI_MODEL` | Gemini 키·모델 (`AQ.`로 시작하면 Vertex AI express로 엶) |
| `LLM_API_KEY`(또는 `ANTHROPIC_API_KEY`) · `LLM_MODEL_STRONG` | Anthropic 키·모델 (기본 `claude-opus-5-5`) |
| `MEASURETRACE_OFFLINE=1` | 캐시만 쓰고 API는 부르지 않음 (토큰 0) |
| `MEASURETRACE_WORKSPACE` | 작업 폴더를 다른 곳으로 (시험·리허설용) |
| `MT_LLM_FALLBACK=0` | 뒷단 서버 측 fallback 끄기 |
| `MT_SMOKE_REWRITES` | 2-1c 합성 데이터 검사 실패 시 코드 초안을 다시 받는 최대 횟수 (기본 2) |
